Thread B / Security Boundary / Identity and Access Model

The control boundary that makes Platform A/B enterprise-ready.

This page defines how COBIT-Chain moves from a local password-protected prototype into an enterprise identity model using Entra ID, RBAC, managed identity, Key Vault, role-specific APIs, MCP tool identity, wearable read-only access, and privileged action controls.
Identity principle: Trust data must never be exposed the same way to every user, AI tool, wearable device, or admin. Every request should have a caller, a role, an allowed scope, an evidence boundary, and an audit trail. Platform A can use a password gate; Platform B must use identity-aware access control.

Identity Control Layers

These layers define who or what can access platform services, what they can see, and what they are allowed to do.

Security architecture
Layer 01

User Identity

Human users authenticate and receive access based on role, site, module, and allowed evidence depth.

  • Viewer
  • Engineer
  • Owner
  • QA/Admin
Layer 02

Application Identity

The app should use managed identity to access storage, secrets, telemetry, and future Azure services.

  • Managed identity
  • Storage access
  • Key Vault access
  • No hard-coded secrets
Layer 03

MCP Tool Identity

AI tools must identify themselves before retrieving evidence, querying trust state, or checking action authority.

  • Tool ID
  • Caller context
  • Allowed scope
  • Replay logging
Layer 04

Wearable Identity

Governance Vision should operate as a read-only, role-filtered, privacy-safe point-of-work interface.

  • Read-only scope
  • HUD response
  • Privacy boundary
  • Escalation only
Layer 05

Privileged Action Guard

Any future write or controlled action must pass role, authority, change-control, validation, and evidence checks.

  • Allow
  • Block
  • Escalate
  • Audit replay

COBIT-Chain Identity and Access Command Center defines the access control model for Platform A/B. It does not replace enterprise IAM, cybersecurity review, QA approval, validation, change control, or formal regulated authorization. Its purpose is to define how the platform should protect evidence, APIs, MCP tools, wearable responses, secrets, and privileged actions as it matures.
