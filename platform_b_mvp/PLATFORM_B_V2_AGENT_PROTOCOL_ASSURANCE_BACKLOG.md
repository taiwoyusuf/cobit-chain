## Candidate capability

Platform B v2 Candidate — Agent Protocol Assurance

## Purpose

Agent Protocol Assurance verifies whether the protocols used by AI agents — MCP, A2A, UCP, AG-UI, A2UI, AP2, or future protocols — are appropriate for the interaction pattern, governed by risk, bounded by authority, monitored for misuse, and linked to evidence before agentic activity creates consequence.

The assurance concern is not only whether an agent protocol enables connection, tool access, agent-to-agent communication, UI generation, payment authorization, or workflow execution.

The assurance concern is whether the protocolized interaction remains governed from connection to consequence.

## Core v2 question

Is this agent using the right protocol for the right interaction pattern, under the right authority, with the right evidence and consequence boundary?

## v2 candidate concepts

### 1. Agent Protocol Assurance Matrix

Maps each protocol to its:

- risk surface
- interaction pattern
- required controls
- evidence requirements
- allowed consequence level
- authority requirement
- human oversight requirement
- observability requirement
- misuse pattern
- recovery requirement

Candidate protocols include:

- MCP
- A2A
- UCP
- AG-UI
- A2UI
- AP2
- future agent protocols

### 2. Protocol-to-Consequence Mapping

Links protocol usage to the possible consequence, including:

- data retrieval
- tool execution
- agent collaboration
- UI generation
- user input capture
- commerce action
- payment authorization
- approval
- record update
- workflow update
- regulated workflow action

This prevents treating all protocols as equal-risk connectors.

### 3. Protocol Selection Risk Gate

Checks whether the selected protocol is appropriate for the use case before integration begins.

Candidate gate checks include:

- use case fit
- interaction pattern fit
- consequence class
- protocol maturity
- control availability
- observability readiness
- identity model
- authorization model
- human oversight requirement
- recovery requirement
- evidence requirement

### 4. Cross-Protocol Consequence Chain

Tracks when one workflow uses multiple protocols.

Example chain:

A2A agent discovery → MCP tool call → AG-UI human input → AP2 payment authorization

Candidate traceability objects include:

- originating agent
- receiving agent
- protocol used
- tool invoked
- user interaction
- authority check
- policy decision
- payload metadata
- consequence created
- evidence ID
- downstream reliance

### 5. Protocol Misuse Detection

Detects when a protocol is used beyond its intended coordination pattern.

Examples include:

- using a tool-access protocol to create payment-like consequences without payment-grade controls
- using an agent-to-agent protocol to bypass human review
- using UI-generation protocols to capture sensitive input without proper disclosure
- using retrieval protocols to support unauthorized decision-making
- chaining protocols to create consequence outside the approved workflow

### 6. Protocol Evidence Envelope

Captures the evidence generated by protocol-based interaction.

Candidate envelope fields include:

- protocol type
- protocol version
- agent identity
- user identity or role context
- tool or resource accessed
- interaction pattern
- authority check
- policy decision
- payload metadata
- response metadata
- human input or approval
- outcome
- consequence class
- evidence ID
- timestamp
- accountable owner

### 7. Protocol Authority Boundary

Defines what an agent may:

- discover
- request
- display
- generate
- retrieve
- invoke
- purchase
- approve
- update
- execute
- delegate

through each protocol.

This prevents protocol access from becoming uncontrolled authority.

### 8. Protocol Runtime Observability

Monitors protocol activity, including:

- protocol calls
- latency
- failures
- retries
- agent-to-agent delegation
- user approvals
- payment attempts
- tool calls
- abnormal protocol sequences
- escalation events
- denied actions
- unexpected consequence chains

### 9. Protocol-Specific Human Oversight

Defines when human input, review, approval, confirmation, or escalation is required based on protocol and consequence type.

Candidate oversight patterns include:

- no human review required
- human confirmation required
- human approval required
- expert review required
- supervisor escalation required
- regulated reviewer sign-off required
- execution blocked until review

### 10. Protocol-to-Right-to-Rely Link

Determines whether the protocol pathway produced enough evidence for a person, system, business process, or regulator to rely on the resulting output or action.

Candidate reliance checks include:

- protocol fit
- authority match
- policy compliance
- evidence completeness
- traceability
- human oversight
- consequence boundary
- recovery feasibility
- auditability
- residual risk

## Protected doctrine

Protocols connect agents.

Assurance governs what those connections are allowed to become.

## Stronger doctrine

The protocol is not the control.

The control is whether the protocolized interaction remains bounded, evidenced, and legitimate.
